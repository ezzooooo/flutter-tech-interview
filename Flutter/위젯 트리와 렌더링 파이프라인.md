## 1. Flutter의 3가지 트리

Flutter는 내부적으로 **3개의 트리**를 사용하여 UI를 관리합니다.

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ Widget Tree │ ──→ │ Element Tree│ ──→ │ RenderObject│
│             │     │             │     │    Tree     │
│ (설계도)      │     │ (관리자)      │     │ (실제 렌더)   │
└─────────────┘     └─────────────┘     └─────────────┘

  "무엇을 그릴지"    "위젯과 렌더를"     "어떻게 그릴지"
   설명하는 설정      연결하는 중개자      실제 레이아웃/페인팅
```

### 1.1 Widget Tree (위젯 트리)

**위젯 트리**는 UI의 **설계도(Blueprint)**입니다.

- 위젯은 **불변(immutable)** 객체
- UI의 구조와 구성을 **선언적으로 설명**
- 상태가 변경되면 **새로운 위젯 인스턴스가 생성**됨 (기존 위젯을 수정하지 않음)
- 매우 가벼운 객체 (생성/폐기 비용이 낮음)

```dart
// 위젯 트리 예시
Scaffold(                          // ← 루트 위젯
  appBar: AppBar(                  //   ├── AppBar
    title: Text('Home'),           //   │   └── Text
  ),                               //   │
  body: Column(                    //   ├── Column
    children: [                    //   │
      Text('Hello'),               //   │   ├── Text
      ElevatedButton(              //   │   └── ElevatedButton
        onPressed: () {},          //   │       └── Text
        child: Text('Click'),     //   │
      ),                           //   │
    ],                             //   │
  ),                               //   │
  floatingActionButton:            //   └── FloatingActionButton
    FloatingActionButton(          //       └── Icon
      onPressed: () {},            //
      child: Icon(Icons.add),      //
    ),                             //
)
```

```
위젯 트리 구조:

Scaffold
├── AppBar
│   └── Text('Home')
├── Column
│   ├── Text('Hello')
│   └── ElevatedButton
│       └── Text('Click')
└── FloatingActionButton
    └── Icon(Icons.add)
```

### 1.2 Element Tree (엘리먼트 트리)

**엘리먼트 트리**는 Widget Tree와 RenderObject Tree를 **연결하는 중개자**입니다.

- 위젯의 **인스턴스화된 표현**
- 위젯 트리의 특정 위치에 대한 **참조를 유지**
- 위젯이 재생성되어도 **Element는 재사용** 가능 (성능 최적화 핵심)
- `BuildContext`는 실제로 **Element** 객체임

```dart
// Widget은 불변이지만, Element는 재사용됨
// 1차 빌드
Text('Count: 0')  →  StatelessElement  →  RenderParagraph
                            ↓
// setState 후 재빌드
Text('Count: 1')  →  StatelessElement(재사용!)  →  RenderParagraph(업데이트)
                     (같은 Element가 새 Widget 참조)
```

**Element의 역할:**

1. Widget과 RenderObject 사이의 **연결고리**
2. Widget Tree의 **위치 정보** 관리
3. 부모-자식 **관계** 유지
4. Widget 변경 시 **업데이트 여부 판단** (`canUpdate`)

```dart
// Element가 위젯 업데이트 여부를 판단하는 로직
static bool canUpdate(Widget oldWidget, Widget newWidget) {
  return oldWidget.runtimeType == newWidget.runtimeType
      && oldWidget.key == newWidget.key;
}

// runtimeType과 key가 같으면 → Element 재사용 (업데이트)
// 다르면 → Element 폐기 후 새로 생성
```

### 1.3 RenderObject Tree (렌더 오브젝트 트리)

**RenderObject Tree**는 실제로 **레이아웃 계산과 화면 페인팅**을 담당합니다.

- 각 RenderObject는 **크기, 위치, 그리기 방법**을 알고 있음
- 무거운 객체 (생성 비용이 높음)
- 가능한 한 **재사용**되도록 설계됨

```
RenderObject Tree 역할:

1. Layout (레이아웃)
   - 부모가 자식에게 제약 조건(Constraints) 전달
   - 자식이 크기(Size) 결정하여 부모에게 반환
   - 부모가 자식의 위치(Offset) 결정

2. Paint (페인팅)
   - Canvas에 실제 픽셀 그리기
   - 배경색, 텍스트, 이미지 등 렌더링

3. Hit Testing
   - 터치 이벤트가 어떤 위젯에 해당하는지 판단
```

### 1.4 세 트리의 관계

```
Widget Tree          Element Tree          RenderObject Tree
(설계도)              (관리자)               (실제 렌더링)

Scaffold     ──→    ScaffoldElement    ──→  RenderFlex
  │                      │                      │
  ├─ AppBar  ──→    StatefulElement   ──→  RenderFlex
  │   │                  │                      │
  │   └─ Text ──→  StatelessElement  ──→  RenderParagraph
  │                      │
  ├─ Column  ──→    MultiChildElement ──→  RenderFlex
  │   │                  │                      │
  │   ├─ Text ──→  StatelessElement  ──→  RenderParagraph
  │   │                  │
  │   └─ Button──→ StatefulElement   ──→  RenderBox
  │
  └─ FAB     ──→    StatefulElement   ──→  RenderBox

• Widget: 불변, 가벼움, 자주 재생성
• Element: 가변, 재사용, 트리 위치 관리
• RenderObject: 무거움, 재사용, 실제 렌더링
```

## 2. 위젯이 화면에 그려지기까지의 과정

### 2.1 렌더링 파이프라인 전체 흐름

```
사용자 입력 / setState() 호출
         │
         ▼
┌─────────────────────┐
│  1. Build Phase     │  위젯 트리 구성/재구성
│     (빌드 단계)       │  → Element 생성/업데이트
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│  2. Layout Phase    │  크기 계산, 위치 결정
│     (레이아웃 단계)    │  → Constraints ↓, Size ↑
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│  3. Paint Phase     │  Canvas에 픽셀 그리기
│     (페인트 단계)      │  → Layer Tree 생성
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│  4. Compositing     │  Layer를 합성하여
│     (합성 단계)       │  → GPU로 전송
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│  5. Rasterize       │  GPU가 실제 픽셀로
│     (래스터화)        │  → 화면에 표시
└─────────────────────┘
```

### 2.2 Build Phase (빌드 단계)

`build()` 메서드가 호출되어 **위젯 트리를 구성**하는 단계입니다.

```dart
// setState() 호출 시 빌드 과정
class CounterWidget extends StatefulWidget {
  @override
  _CounterWidgetState createState() => _CounterWidgetState();
}

class _CounterWidgetState extends State<CounterWidget> {
  int _count = 0;

  void _increment() {
    setState(() {  // 1. setState 호출
      _count++;    // 2. 상태 변경
    });
    // 3. 위젯이 "dirty"로 표시됨
    // 4. 다음 프레임에서 build() 재호출
  }

  @override
  Widget build(BuildContext context) {
    // 5. 새로운 위젯 트리 생성
    return Column(
      children: [
        Text('Count: $_count'),  // 새 Text 위젯 인스턴스 생성
        ElevatedButton(
          onPressed: _increment,
          child: const Text('Increment'),  // const → 재사용
        ),
      ],
    );
  }
}
```

**빌드 단계에서 일어나는 일:**

```
1. 새 Widget 인스턴스 생성
2. Element가 canUpdate() 호출하여 기존 Element 재사용 가능 여부 확인
3. 재사용 가능하면 → Element.update(newWidget)
   재사용 불가능하면 → 기존 Element 폐기, 새 Element 생성
4. 필요 시 RenderObject 업데이트
```

### 2.3 Layout Phase (레이아웃 단계)

**크기와 위치를 계산**하는 단계입니다. **Constraints go down, Sizes go up** 원칙을 따릅니다.

```
부모 위젯
│
│  ① Constraints go down (제약 조건 전달)
│  "너의 최소 너비는 100, 최대 너비는 300이야"
│
▼
자식 위젯
│
│  ② Size go up (크기 결정 후 보고)
│  "나는 200x50 크기로 결정했어"
│
▼
부모 위젯
│
│  ③ Parent sets position (위치 결정)
│  "너를 (10, 20) 위치에 배치할게"
│
▼
완료
```

```dart
// 제약 조건 예시
Container(
  width: 200,   // 고정 크기 = tight constraint
  height: 100,
  child: Text('Hello'),  // Text는 200x100 내에서 렌더링
)

// 유연한 제약 조건
ConstrainedBox(
  constraints: BoxConstraints(
    minWidth: 100,
    maxWidth: 300,
    minHeight: 50,
    maxHeight: 200,
  ),
  child: Text('Hello'),  // Text가 자신의 크기를 결정
)
```

**BoxConstraints의 구조:**

```dart
class BoxConstraints {
  final double minWidth;
  final double maxWidth;
  final double minHeight;
  final double maxHeight;

  // Tight Constraint: min == max (크기 고정)
  // Loose Constraint: min == 0 (자유롭게 크기 결정)
  // Unbounded: max == double.infinity (무제한)
}
```

### 2.4 Paint Phase (페인트 단계)

RenderObject의 `paint()` 메서드가 호출되어 **Canvas에 실제 픽셀을 그리는** 단계입니다.

```dart
// CustomPainter로 직접 페인팅 예시
class MyPainter extends CustomPainter {
  @override
  void paint(Canvas canvas, Size size) {
    final paint = Paint()
      ..color = Colors.blue
      ..style = PaintingStyle.fill;

    // 원 그리기
    canvas.drawCircle(
      Offset(size.width / 2, size.height / 2),
      50,
      paint,
    );

    // 텍스트 그리기
    final textPainter = TextPainter(
      text: const TextSpan(text: 'Hello', style: TextStyle(color: Colors.white)),
      textDirection: TextDirection.ltr,
    )..layout();
    textPainter.paint(canvas, Offset(size.width / 2 - 20, size.height / 2 - 8));
  }

  @override
  bool shouldRepaint(covariant CustomPainter oldDelegate) => false;
}
```

**페인팅 순서:**

1. 자기 자신을 먼저 그림 (배경 등)
2. 자식 위젯들을 그림 (z-order 순서)
3. 전경 장식을 그림

### 2.5 Compositing & Rasterization (합성 및 래스터화)

```
Paint Phase 결과 → Layer Tree 생성
                      │
                      ▼
              Compositing (합성)
              여러 Layer를 하나로 합침
                      │
                      ▼
              Rasterization (래스터화)
              Skia/Impeller 엔진이 GPU에서
              실제 픽셀로 변환
                      │
                      ▼
              화면에 표시 (60fps / 120fps)
```

**Impeller (Flutter 3.x 기본 엔진):**

- Skia를 대체하는 Flutter의 새로운 렌더링 엔진
- 셰이더 사전 컴파일로 **jank(끊김) 제거**
- iOS에서 기본 활성화, Android에서 점진적 도입

## 4. 면접 예상 질문

### Q1: "Flutter에서 위젯 트리란 무엇인가요?"

**답변**: 위젯 트리는 Flutter 앱의 **UI 구조를 설명하는 계층적 트리**입니다. 모든 Flutter UI는 위젯의 중첩으로 구성되며, 이 위젯들이 부모-자식 관계를 이루어 트리 구조를 형성합니다. 위젯은 불변 객체로, UI의 "설계도" 역할을 합니다. Flutter는 이 위젯 트리 외에도 Element Tree(관리자 역할)와 RenderObject Tree(실제 렌더링)를 함께 사용하여 효율적으로 UI를 업데이트합니다.

#### 꼬리질문: "Widget Tree, Element Tree, RenderObject Tree의 차이는?"

**답변**: 세 트리는 각각 다른 역할을 합니다:

- **Widget Tree**: UI의 "설계도"입니다. 불변이며 가벼운 객체로, 상태 변경 시 새로 생성됩니다. `build()` 메서드의 결과물입니다.
- **Element Tree**: Widget과 RenderObject를 연결하는 "관리자"입니다. 트리의 위치 정보를 유지하고, 위젯이 재생성되어도 Element는 재사용되어 성능을 최적화합니다. `BuildContext`가 바로 Element입니다.
- **RenderObject Tree**: 실제 레이아웃 계산과 화면 페인팅을 담당합니다. 무거운 객체이므로 가능한 한 재사용됩니다.

핵심은 Widget이 자주 재생성되어도 Element와 RenderObject가 재사용되어 **실제 렌더링 비용이 최소화**된다는 점입니다.

#### 꼬리질문: "위젯이 불변인데 어떻게 UI가 변경되나요?"

**답변**: Widget 자체는 불변이지만, **새로운 Widget 인스턴스가 생성**됩니다. `setState()` 호출 시 `build()` 메서드가 다시 실행되어 새로운 위젯 트리가 만들어집니다. Flutter는 이전 트리와 새 트리를 비교(diffing)하여, 변경된 부분만 Element와 RenderObject를 업데이트합니다. 이때 `canUpdate()` 메서드가 `runtimeType`과 `key`를 비교하여 Element 재사용 여부를 결정합니다. 이 메커니즘 덕분에 선언적 UI의 장점(명확성, 예측 가능성)과 명령형 UI의 장점(성능)을 모두 얻습니다.

#### 꼬리질문: "Key가 위젯 트리에서 하는 역할은?"

**답변**: Key는 Element가 위젯을 **식별하는 데 사용**하는 값입니다. `canUpdate()` 메서드에서 `runtimeType`과 함께 Key를 비교합니다.

Key가 없으면 같은 타입의 위젯은 순서만으로 매칭됩니다. 리스트에서 아이템 순서가 변경되면 잘못된 Element와 매칭될 수 있습니다.

```dart
// ❌ Key 없음 - 순서 변경 시 상태 혼란
ListView(children: items.map((item) => ItemWidget(item: item)).toList())

// ✅ Key 사용 - 올바른 상태 유지
ListView(children: items.map((item) => ItemWidget(key: ValueKey(item.id), item: item)).toList())
```

`ValueKey`는 값 기반, `ObjectKey`는 객체 참조 기반, `UniqueKey`는 항상 고유한 Key입니다. `GlobalKey`는 위젯 트리 전체에서 고유하며 상태 접근이나 위젯 이동에 사용됩니다.

### Q2: "위젯이 화면에 그려지기까지의 과정을 설명해보세요."

**답변**: Flutter의 렌더링 파이프라인은 5단계로 구성됩니다:

1. **Build Phase**: `build()` 메서드가 실행되어 위젯 트리를 구성합니다. Element가 Widget의 변경 여부를 판단하고, RenderObject를 생성/업데이트합니다.

2. **Layout Phase**: "Constraints go down, Sizes go up" 원칙에 따라 부모가 제약 조건을 자식에게 전달하고, 자식이 크기를 결정하여 보고하면, 부모가 자식의 위치를 결정합니다.

3. **Paint Phase**: 각 RenderObject가 Canvas에 실제 픽셀을 그립니다. 배경, 자식, 전경 순서로 그려집니다.

4. **Compositing**: 여러 Layer를 하나로 합성합니다. RepaintBoundary 등으로 분리된 레이어가 합쳐집니다.

5. **Rasterization**: Impeller(또는 Skia) 엔진이 GPU를 사용하여 최종 픽셀로 변환하고 화면에 표시합니다.

이 과정이 초당 60회(또는 120회) 반복되어 부드러운 애니메이션이 가능합니다.

#### 꼬리질문: "Constraints go down, Sizes go up이란?"

**답변**: Flutter 레이아웃의 핵심 원칙입니다. 부모 위젯이 자식에게 **"네가 가질 수 있는 최소/최대 크기"라는 제약 조건(Constraints)을 아래로 전달**합니다. 자식은 그 범위 내에서 자신의 크기를 결정하고 **결정된 크기(Size)를 위로 보고**합니다. 마지막으로 부모가 자식의 **위치(Offset)를 결정**합니다.

예를 들어 `Container(width: 200)`은 자식에게 "너비가 정확히 200이어야 해"라는 tight constraint를 전달합니다. `Expanded`는 남은 공간을 모두 차지하라는 constraint를 전달합니다. 이 과정이 트리 전체에 걸쳐 한 번의 패스로 완료되어 O(n) 시간에 레이아웃이 계산됩니다.

#### 꼬리질문: "setState() 호출 후 화면 업데이트까지 무슨 일이 일어나나요?"

**답변**: 단계별로 설명하면:

1. `setState()` 내부 콜백이 **동기적으로 실행**되어 상태 변경
2. 해당 State 객체의 Element가 **"dirty"로 표시**됨
3. Flutter 엔진의 **다음 프레임 스케줄링**에 등록
4. 다음 VSync 신호에서 **Build Phase** 시작 - `build()` 재호출
5. Element가 `canUpdate()`로 기존 위젯과 비교
6. 변경된 RenderObject만 **Layout Phase** 수행
7. 변경된 영역만 **Paint Phase**에서 다시 그림
8. **Compositing → Rasterization** 후 화면 표시

핵심은 "변경된 부분만" 업데이트한다는 점입니다. Flutter는 dirty로 표시된 Element의 서브트리만 재빌드하고, 변경된 RenderObject만 re-layout/re-paint합니다.

#### 꼬리질문: "리빌드(rebuild)와 리페인트(repaint)의 차이는?"

**답변**:

- **Rebuild**: `build()` 메서드를 다시 호출하여 새로운 Widget 인스턴스를 생성하는 것입니다. Widget 트리의 구조가 변경될 수 있습니다. `setState()`, `ref.watch()` 변경 시 발생합니다.
- **Repaint**: RenderObject가 Canvas에 다시 그리는 것입니다. Widget 트리 구조는 그대로이고, 시각적 표현만 변경됩니다. 예를 들어 색상만 변경되거나 애니메이션 프레임이 갱신될 때 발생합니다.

Rebuild이 항상 Repaint를 유발하지는 않습니다. `canUpdate()`로 같은 위젯이라고 판단되면 Rebuild만 일어나고 Repaint는 발생하지 않을 수 있습니다. 반대로 `CustomPainter`의 `shouldRepaint()`가 true를 반환하면 Rebuild 없이 Repaint만 일어날 수 있습니다.

#### 꼬리질문: "렌더링 성능을 최적화하는 방법은?"

**답변**: 주요 최적화 방법은 다음과 같습니다:

1. **const 생성자 사용**: 불변 위젯은 재생성되지 않아 Build Phase를 건너뜁니다
2. **위젯 분리**: 상태 변경이 필요한 부분만 별도 위젯으로 분리하여 리빌드 범위 최소화
3. **RepaintBoundary**: 자주 리페인트되는 위젯(애니메이션 등)을 분리하여 다른 위젯에 영향 방지
4. **ListView.builder 사용**: Lazy loading으로 화면에 보이는 위젯만 빌드
5. **shouldRepaint/shouldRebuild 활용**: 불필요한 리빌드/리페인트 방지
6. **itemExtent 지정**: ListView의 아이템 높이를 미리 지정하여 레이아웃 계산 최적화

## 5. 심화: Flutter의 프레임 처리

### Vsync와 프레임

```
16.67ms (60fps) 또는 8.33ms (120fps)
┌─────────────────────────────────────┐
│ Build │ Layout │ Paint │ Composite  │
│  3ms  │  2ms   │  2ms  │   1ms     │ = 약 8ms (여유 있음)
└─────────────────────────────────────┘

프레임 시간을 초과하면 "jank" 발생 (화면 끊김)
```

### 프레임 드롭 방지

```dart
// ❌ 메인 스레드에서 무거운 작업
void _processData() {
  setState(() {
    // 100만 건 데이터 처리 → 프레임 드롭!
    _results = heavyComputation(rawData);
  });
}

// ✅ Isolate에서 무거운 작업 처리
Future<void> _processData() async {
  setState(() => _isLoading = true);

  // 별도 Isolate에서 실행
  final results = await compute(heavyComputation, rawData);

  setState(() {
    _results = results;
    _isLoading = false;
  });
}
```
